# Phase 6.2 — Implement OpenRouter and Application Tool Calling

## Role

Act as a Senior Full-Stack AI Engineer specializing in TypeScript, OpenRouter, structured tool calling, and secure application integration.

Implement the approved architecture from Phase 6.1.

This is an incremental upgrade of an existing working application.

## 1. Read the project

Read:

- `AGENTS.md`
- `docs/ai-integration-plan.md`
- `docs/ai-tool-registry.md`
- `docs/ai-security-design.md`
- `docs/ai-implementation-checklist.md`
- Existing assistant and module services
- Existing tests

Follow the architecture decisions established in Phase 6.1.

Do not rebuild the application.

## 2. Load the existing environment variables

The project already has a `.env` file containing:

- `OPENROUTER_API_KEY`
- `OPENROUTER_MODEL`

Use the existing values.

Do not ask me to paste the API key.

Do not create a replacement API key.

Do not hardcode the model name.

Configure the backend to load the existing `.env` securely.

Requirements:

- The key must remain server-side.
- Never expose the key in browser JavaScript.
- Never include the key in API responses.
- Never print the key in logs.
- Ensure `.env` is gitignored.
- Provide clear startup errors when configuration is missing.
- Support model changes by editing `OPENROUTER_MODEL`, without modifying source code.

Do not use a `VITE_` prefix for secrets.

## 3. Implement the OpenRouter backend

Create a minimal Node.js/TypeScript backend consistent with the Phase 6.1 plan.

Implement:

- OpenRouter chat completion requests
- Configurable model selection
- Conversation messages
- Structured tool calling
- Tool-call argument validation
- Tool-result handling
- Bounded tool execution loops
- Timeouts
- Rate-limit handling
- Request cancellation where practical
- Safe error messages
- Basic token usage and cost reporting where available

Use OpenRouter's documented API format.

Avoid unnecessary dependencies.

## 4. Connect the assistant to current application state

Implement the data-access architecture approved in Phase 6.1.

The assistant must retrieve current data from the existing application.

Examples:

- A uniform is issued, and inventory decreases.
- The assistant subsequently reports the updated quantity.
- A purchase order is received, and inventory increases.
- The assistant reports the new quantity.
- A locker is assigned.
- The assistant no longer reports it as available.

Do not create a separate static AI-only dataset.

Do not allow the LLM to invent record values.

Enforce the approved authorization boundary.

Do not treat browser-provided role claims as authenticated identity.

## 5. Implement read-only tools

Create a typed tool registry using existing domain services.

Support relevant operations for:

### Uniform Management

- Search products
- Search inventory
- Filter by size, category, or department
- Retrieve issuance history
- Check issuance eligibility

### Purchase Support

- Search purchase requests
- Retrieve purchase order status
- Retrieve simulated supplier/product mappings
- Retrieve goods-receipt information

### Locker Management

- Search available lockers
- Retrieve assignments
- Retrieve allocation history

### Document Lookup

- Search accessible documents
- Retrieve permitted document metadata
- Retrieve relevant document passages

Document retrieval can initially use the existing retrieval service; Phase 6.3 will upgrade it.

Every tool must have:

- A stable name
- A clear description
- A validated input schema
- A typed result
- Permission checks
- Explicit not-found behavior
- Bounded result sizes

## 6. Implement natural-language understanding

The assistant should understand ordinary Vietnamese questions without requiring exact keywords.

Example questions:

- "Kho còn bao nhiêu áo blouse nữ cỡ L?"
- "Nhân viên này còn được cấp đồng phục không?"
- "Có đơn mua hàng nào đang chờ duyệt?"
- "Tủ nào ở tầng 3 đang trống?"
- "Mã sản phẩm này có tương ứng với mã nhà cung cấp nào?"
- "Tại sao yêu cầu cấp phát này bị từ chối?"
- "Sau khi nhập hàng, tồn kho thay đổi thế nào?"

Support follow-up questions that depend on previous conversation context.

When the user provides an ambiguous name, product, or code, ask for clarification instead of guessing.

## 7. Keep business logic deterministic

The LLM may interpret questions, choose tools, and explain tool results.

It must not independently decide:

- Inventory quantities
- Issuance eligibility
- Purchasing limits
- Approval outcomes
- Financial calculations
- Transaction states

These must come from existing application services.

Tool calling must be read-only in this phase.

The assistant must never silently create or approve transactions.

## 8. Preserve fallback behavior

Keep the existing deterministic assistant available.

If OpenRouter fails:

- Show a clear status.
- Avoid fabricating an LLM answer.
- Offer supported deterministic responses where possible.
- Preserve conversation and application state.

Make fallback mode distinguishable in the UI or response metadata.

## 9. Testing

Add Vitest tests covering:

- Permission enforcement
- Invalid arguments
- Ambiguous records
- Updated inventory state
- Tool execution limits
- OpenRouter error handling
- Fallback behavior

Mock OpenRouter in automated tests.

Do not require real paid API calls for the normal test suite.

Run TypeScript checks, unit tests, and production build.

Implement the working OpenRouter assistant backend and frontend connection.

Update relevant documentation.
