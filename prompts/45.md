# Phase 4.5 — Real-World Excel Analysis and Prototype Alignment

## Role

Act as a **Senior Enterprise Solution Architect, Data Engineer, Business Analyst, and Full-Stack Engineer** experienced in hospital administrative systems, Excel-based operational workflows, and enterprise application modernization.

You are working on the existing **Vinmec Administrative Super App prototype**.

The application has already been implemented and completed its initial QA phase (Prompts 1–4).

Your task is to analyze a newly provided real-world Excel workbook and use its structure, business logic, and workflow evidence to improve the existing application.

**This is an incremental improvement task, not a new application development task.**

## 1. Sources and Priorities

Inspect the repository and locate:

- `AGENTS.md`
- The original Vietnamese project proposal (proposal.md)
- The newly added Excel workbook(s) named uniform_manage.xlsx
- `docs/requirements.md`
- `docs/architecture.md`
- `docs/data-model.md`
- `docs/implementation-plan.md`
- Existing application source code and tests

Use the sources in this order:

1. **AGENTS.md:** Project development and safety instructions.
2. **Project proposal:** Primary reference for functional scope and intended capabilities.
3. **Excel workbook:** Primary evidence of actual data structure, terminology, and existing operational practices.
4. **Existing application:** Current implementation to be updated rather than rebuilt.
5. **Planning documents:** Existing architectural decisions and assumptions.

When the proposal, workbook, and implementation disagree, explicitly document the discrepancy.

Do not silently overwrite business rules or assume that the workbook is always correct.

## 2. Important Constraints

This remains a fully simulated prototype.

- No real SAP integration.
- No real hospital databases or APIs.
- No external LLM services.
- No real authentication services.
- No production deployment requirements.
- All displayed employee information, contracts, transactions, histories, and financial values must be synthetic.
- Preserve existing working features and workflows.
- Do not rebuild the project from scratch.
- Do not introduce unnecessary frameworks or infrastructure.
- Use the existing React, TypeScript, localStorage, and mock-service architecture.

### Data Privacy

The Excel workbook may contain confidential operational data or personally identifiable information.

Treat the workbook as sensitive reference material.

Do not:
- Copy real employee names, IDs, phone numbers, or personal details into application fixtures.
- Reproduce confidential contracts, prices, financial records, or supplier information verbatim.
- Display raw workbook rows in the UI.
- Send workbook contents to external APIs or LLM providers.
- Include sensitive records in screenshots, logs, documentation, or automated test outputs.
- Commit the reference workbook to Git unless explicitly authorized.

Use structure, relationships, field formats, formulas, and business logic as references.

Generate new fictional records that reflect the observed data model and workflow.

If the workbook contains sensitive records that cannot be safely processed in the current environment, report the limitation and work from an authorized sanitized copy instead.

## 3. Analyze Every Worksheet

Perform a thorough structural and functional analysis of the workbook.

Do not merely convert the Excel file to CSV.

Inspect:

### Workbook Structure

- Sheet names and their apparent purposes
- Column headers
- Data types
- Required and optional fields
- Unique identifiers
- Repeated identifiers across sheets
- Hidden sheets, rows, or columns where accessible
- Named ranges
- Data validation rules
- Dropdown lists
- Cell formatting that conveys meaning
- Lookup tables
- Cross-sheet references
- Formulas and calculated fields

### Business Information

Identify relevant entities such as:

- Employees
- Departments
- Employee roles
- Uniform categories
- Product codes
- Product sizes
- Inventory quantities
- Issuance records
- Request records
- Suppliers
- Purchase prices
- Purchasing transactions
- Approval information

These are examples, not assumptions about the workbook's contents.

Only describe entities and fields actually supported by the Excel data.

### Workflow Evidence

Investigate whether the workbook reveals:

- How uniform requests are recorded
- How inventory is tracked
- How issuance history is maintained
- How employee eligibility is determined
- How purchasing quantities are calculated
- How reports are consolidated
- How product codes are mapped
- How approvals or confirmations are represented
- How dates, prices, and quantities are updated

Distinguish between:

1. Explicit workbook fields or formulas
2. Strongly suggested operational patterns
3. Unverified interpretations

Do not invent workflow rules solely because a column name seems to imply them.

## 6. Update the Existing Application

Implement the necessary changes identified in the alignment plan.

### Data Models

- Update TypeScript interfaces and types.
- Preserve stable identifiers and relationships.
- Update services to support revised structures.
- Avoid duplicate sources of truth.
- Ensure historical records preserve relevant values at the time of the transaction.

### Uniform Management

Where supported by the workbook, align:

- Product catalog structure
- Uniform categories
- Product codes
- Sizes
- Employee-role eligibility
- Department associations
- Stock records
- Issuance records
- Issuance limits
- Historical purchase prices
- Inventory reporting
- Department-level reporting

Preserve the proposal's configurable default issuance limit of 3 sets per employee per year unless there is explicit evidence requiring a different assumption.

Preserve the configurable proposed reserve purchasing cap of 40%.

If the workbook clarifies how these limits should be calculated, update the implementation and document the evidence.

If it does not, retain the existing configurable assumption.

### Purchase Support

Where applicable:

- Align product-code structures.
- Improve internal-to-supplier code mappings.
- Update product descriptions and categories.
- Refine simulated product matching.
- Adjust purchase request fields.
- Maintain consistent purchasing and inventory workflows.

SAP must remain fully simulated.

### Other Modules

Only modify Document Lookup or Locker Management if the Excel evidence is relevant.

Do not make unrelated changes.

## 7. Generate Realistic Synthetic Data

Replace or extend the existing fictional dataset using patterns learned from the workbook.

Preserve realistic:

- Entity relationships
- Product categorization
- Size distributions
- Number and date formats
- Inventory and issuance patterns
- Record lifecycle states
- Operational edge cases

However, do not copy identifiable or confidential records from the original workbook.

Use fictional employee identities, product identifiers, supplier information, and transaction records.

The dataset should include:

- Employees who have reached issuance limits
- Employees still eligible for issuance
- Products with sufficient inventory
- Products requiring replenishment
- Historical issuance records
- Pending and completed purchasing requests

Use one canonical seed dataset shared by the modules.

2. Add versioning or migration logic where necessary.
3. Preserve compatible existing records.
4. Handle incompatible records safely.
5. Avoid silently deleting user-generated demo data.
6. Keep the Reset Demo Data function working.

If a full reset is unavoidable because of incompatible schema changes, document why and provide an explicit reset path.
