- Sidebar navigation with module icons

## Module 1: Uniform Management

Implement:

### Catalog and Inventory
- Uniform catalog with product codes, names, types, sizes, and prices
- Department and employee-role associations
- Inventory quantities by product and size
- Stock adjustment and movement history
- Low-stock alerts
- Supplier product-code mappings

### Employee Issuance
- Employee directory with department and role
- Individual issuance history
- Issue date, product, size, quantity, and historical unit price
- Configurable issuance limits (default 3 sets per year)
- Eligibility checks based on issuance history
- Exceptions requiring approval
- Inventory deduction only when uniforms are issued

### Requests
- Department-level uniform requests
- Request multiple products and sizes
- Validate employee eligibility
- Check stock availability
- Draft, submit, approve, reject, and fulfill requests
- Display reasons for rejection or ineligibility
- Maintain request history

### Purchasing
- Calculate shortages
- Recommend additional purchasing
- Apply the proposed 40% reserve purchasing cap
- Make business-rule assumptions configurable and document them
- Generate draft purchase requests
- Map internal codes to supplier codes
- Simulate multi-party approval
- Simulate SAP PO creation with mock IDs and statuses

### Reporting
- Reports by department
- Reports by product code
- Reports by size
- Issuance trends
- Inventory summaries
- CSV export

## Cross-Module Consistency

Use shared employees, departments, suppliers, products, and purchasing records.

Examples:
- A uniform shortage should be able to generate a purchase request.
- A confirmed purchase receipt should increase inventory.
- An employee's department should be consistent across modules.
- Approvals should appear in the central approval inbox.
- Important actions should generate audit records.
- Dashboard metrics must reflect actual mock state, not disconnected hardcoded numbers.

## Development Skills and Quality Requirements

### Project Initialization

If the repository does not contain an application, initialize it using React, TypeScript, Vite, Tailwind CSS, and shadcn/ui.

Configure React Router, Lucide icons, Recharts, Vitest, React Testing Library, and Playwright as appropriate.

Install project dependencies locally. Do not install global packages.

### UI/UX Pro Max

Read and apply the installed UI/UX Pro Max skill when designing the application.

Establish a consistent design system before building individual pages.

Apply the same design language across all four modules, the dashboard, approval inbox, and shared chatbot.

Prioritize:
- Professional enterprise UI
- Consistent typography and spacing
- Accessible components and keyboard navigation
- Clear data tables and forms
- Responsive layouts
- Meaningful validation and feedback
- Consistent status indicators

Avoid decorative complexity, excessive gradients, unnecessary animations, and visually inconsistent modules.

### Vitest

Configure Vitest and React Testing Library.

Write automated tests alongside implementation, not only after all modules are complete.

At minimum, cover:
- Uniform issuance limits
- Inventory validation and deductions
- Reserve purchasing calculations
- Historical price preservation
- Multi-party approval transitions
- Locker allocation conflicts
- Supplier product matching
- Document access permissions
- localStorage persistence and reset behavior

Use deterministic test fixtures and reset application state between tests.

### Playwright

Use the installed Playwright skill for browser inspection whenever the environment supports it.

After completing each major module:
1. Start the development server.
2. Open the application in a real browser.
3. Test at least one complete user journey.
4. Capture screenshots.
5. Inspect layout problems and browser errors.
6. Fix issues before proceeding.

Do not claim browser verification if Chromium or the development server cannot run.

### Quality Gates

After each implementation milestone:
- Run relevant Vitest tests.
- Run TypeScript checks.
- Run the production build.
- Fix regressions before continuing.

Do not consider a feature complete merely because its page renders. Its primary interactions must work and its business logic must be tested.

Implement the complete application incrementally.

Run available checks after each major module.

Do not stop after creating the dashboard or basic navigation. Continue until all four modules and shared features are implemented.

Document any limitations or incomplete features honestly.
