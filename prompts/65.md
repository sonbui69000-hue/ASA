# Phase 6.5 — Final AI Verification and Stakeholder Demo Readiness

## Role

Act as a Senior AI Quality Engineer, Security Reviewer, and Healthcare Product QA Lead.

You are conducting final verification of the OpenRouter-powered Vinmec Administrative Super App.

The application already contains:

- Four administrative modules
- Real OpenRouter LLM integration
- Read-only application tools
- Document RAG
- Shared AI assistant UI
- Synthetic operational data
- Simulated SAP workflows

Your goal is to verify that the AI assistant is reliable enough for a stakeholder demonstration.

Do not rebuild the application.

## 1. Inspect the project

Read:

- `AGENTS.md`
- All Phase 6 implementation documents
- Existing application tests
- Existing Playwright tests
- `docs/demo-verification.md`
- Current assistant implementation
- Current RAG implementation
- Current authorization logic

Inspect the actual code and test coverage.

## 2. Verify environment security

The existing `.env` contains:

- `OPENROUTER_API_KEY`
- `OPENROUTER_MODEL`

Verify that:

- The backend loads both values.
- The configured model is used.
- The API key is never sent to the browser.
- The key is absent from the production frontend bundle.
- The key is absent from Git-tracked files.
- The key is not written to logs or screenshots.
- Missing configuration produces a controlled error.
- OpenRouter failures do not crash the application.

Do not print the API key during verification.

## 3. Evaluate natural-language understanding

Create a test dataset of at least 40 realistic Vietnamese questions.

Cover:

- Uniform inventory
- Uniform issuance eligibility
- Employee issuance history
- Purchasing requests
- Purchase order status
- Product-code matching
- Locker availability
- Locker assignments
- Document lookup
- Multi-turn conversations
- Ambiguous entities
- Questions outside the available data

Include paraphrases and informal Vietnamese.

Test whether the assistant chooses the correct tools and uses the correct records.

Do not evaluate success solely by whether an answer sounds fluent.

## 4. Evaluate RAG quality

Test at least 20 document questions.

Evaluate:

- Retrieval relevance
- Citation correctness
- Document version correctness
- Permission filtering
- Evidence sufficiency
- Unsupported claims
- Vietnamese paraphrase handling
- Missing-evidence behavior

Report failures individually.

Do not claim 100% accuracy without measured evidence.

## 5. Test security and misuse cases

Include tests for:

- Unauthorized document access
- Restricted employee records
- Prompt injection in document content
- Attempts to override business rules
- Attempts to reveal API keys
- Attempts to invoke unauthorized tools
- Malformed tool arguments
- Ambiguous employee names
- Fabricated document IDs
- Nonexistent product codes
- Excessive tool-call loops
- API timeouts
- OpenRouter rate limits

Verify that the assistant cannot bypass existing business logic.

Explicitly document any security guarantees that remain prototype-only because identity or state is simulated.

## 6. Test operational consistency

Perform workflows that change application data.

After each workflow, ask the assistant about the affected records.

Test:

1. Uniform issuance decreases stock.
2. Goods receipt increases stock.
3. Purchasing status changes are reflected correctly.
4. Locker assignment changes availability.
5. Document publication updates retrieval.
6. Document withdrawal removes invalid evidence.
7. localStorage reload preserves the expected state.
8. Demo reset restores consistent seed data.

The assistant must reflect the application's current state.

## 7. Automated tests

Run:

- TypeScript checks
- Vitest tests
- Production build
- All existing Playwright tests
- New AI integration tests
- New RAG tests

Mock OpenRouter for deterministic automated regression tests.

Also perform a small, controlled live API smoke test using the configured model, if the environment permits and API usage is authorized.

Keep live API calls limited to avoid unnecessary costs.

Do not run the entire automated suite against the paid API.

If browser execution fails because of sandbox restrictions, request the appropriate permission or document the limitation.

Do not claim tests passed if they were not executed.

## 8. Visual verification

Use Playwright to inspect:

- Assistant conversation interface
- Loading states
- Error states
- Tool-result display
- Document citations
- Cross-module navigation
- Desktop layout
- Mobile layout

Capture screenshots.

Check for browser console errors.

Repair genuine application regressions.

Avoid unrelated redesign.

## 9. Prepare stakeholder demo scenarios

Create five repeatable AI demonstration scenarios.

### Scenario 1 — Uniform inventory

Ask about available uniform quantities using natural Vietnamese.

Demonstrate that the assistant retrieves current inventory rather than inventing quantities.

### Scenario 2 — Issuance eligibility

Ask whether a fictional employee is eligible for additional uniforms.

Demonstrate deterministic business-rule evaluation.

### Scenario 3 — Document RAG

Ask a question using terminology different from the source document.

Demonstrate semantic retrieval, grounded answers, and clickable citations.

### Scenario 4 — Purchasing

Ask about a pending purchase request or purchase order.

Demonstrate accurate status retrieval and navigation.

### Scenario 5 — Cross-module consistency

Perform a normal application action, then ask the assistant about the updated state.

Demonstrate that the assistant reflects the change.

Use only synthetic data.

## 11. Final instructions

Do not fabricate successful test results.

Do not hide unresolved security issues.

Do not claim production-grade authorization if the application still relies on simulated identities.

Do not modify unrelated functionality.

Preserve all existing business rules and module workflows.

At completion, provide a concise assessment of whether the application is ready for a live stakeholder demonstration, supported by actual verification evidence.
