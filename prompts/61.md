# Phase 6.1 — OpenRouter AI Architecture and Integration Plan

## Role

Act as a Senior AI Engineer, Enterprise Solution Architect, and Healthcare Software Architect.

You are upgrading the existing Vinmec Administrative Super App from a deterministic chatbot to a real LLM-powered assistant using OpenRouter.

**This phase is planning and analysis only. Do not implement code yet.**

## 1. Inspect the existing project

Read:

- `AGENTS.md`
- The original project proposal
- `docs/requirements.md`
- `docs/architecture.md`
- `docs/data-model.md`
- `docs/excel-alignment-report.md`, if present
- `docs/demo-verification.md`, if present
- Existing assistant implementation
- Existing document retrieval implementation
- All four module services and data models
- Current localStorage persistence architecture
- Existing tests and Playwright configuration

Inspect the actual repository rather than assuming file names or architecture.

The application already has:

1. Uniform Management
2. Document Lookup
3. Locker Management
4. Purchase Support
5. Shared deterministic AI assistant

All operational data is synthetic, and SAP is simulated.

Preserve these existing capabilities.

## 2. Environment configuration

The project already contains a `.env` file with:

- `OPENROUTER_API_KEY`
- `OPENROUTER_MODEL`

Use these exact environment variable names.

Inspect how the project currently loads environment variables.

Do not print, log, expose, or copy the API key into documentation.

Do not request another API key.

Do not hardcode the model name. The configured model must come from `OPENROUTER_MODEL`.

Plan a secure server-side OpenRouter integration.

Never expose `OPENROUTER_API_KEY` through `VITE_` variables or frontend source code.

Ensure `.env` is excluded from Git.

If the existing model does not support a required capability, document the limitation and propose a compatible fallback without silently switching models.

## 3. Design the AI architecture

Design a minimal Node.js/TypeScript backend for the existing Vite application.

The backend should handle:

- OpenRouter API requests
- Model configuration
- Tool orchestration
- Document retrieval
- Access control
- Response validation
- Error handling
- Request timeouts
- Usage and cost tracking
- Safe logging

Avoid introducing unnecessary infrastructure.

Do not introduce PostgreSQL, Redis, Docker, or cloud services unless there is a compelling technical reason.

## 4. Resolve localStorage and backend data access

The existing application uses browser localStorage as its source of operational state.

A server cannot directly access browser localStorage.

Analyze this limitation carefully.

Propose a minimal architecture that allows the LLM to answer questions about the application's current data.

Requirements:

- Avoid maintaining inconsistent frontend and backend datasets.
- Ensure answers reflect recent user actions.
- Preserve existing module behavior.
- Preserve localStorage persistence where practical.
- Prevent unauthorized access to employee, inventory, locker, and document information.
- Do not trust arbitrary client-supplied role claims.
- Do not allow the model to directly mutate application state.
- Clearly distinguish prototype-only trust assumptions from production security.

Evaluate possible approaches, including a server-authoritative state service and a constrained browser-state bridge.

Recommend the simplest approach that provides coherent demo behavior and meaningful authorization.

Do not describe client-provided role information as secure authentication.

## 5. Design tool calling

The LLM should interpret natural-language questions and select appropriate application tools.

Propose a tool registry supporting operations such as:

- Search uniform inventory
- Find product by code, size, or category
- Check employee issuance eligibility
- Retrieve employee issuance history
- Retrieve purchasing requests
- Retrieve purchase order status
- Search available lockers
- Retrieve locker assignments
- Search internal documents
- Retrieve document passages

Use actual existing services and data structures.

Tool inputs and outputs must be validated.

Business calculations must remain deterministic.

For the initial implementation, tools should be read-only. Any future write operation must require explicit user confirmation and application-level validation.

## 6. Design the RAG pipeline

The existing document search is keyword-based.

Design a real retrieval-augmented generation pipeline that supports:

- Vietnamese text
- Document chunking
- Metadata
- Version filtering
- Permission filtering
- Keyword retrieval
- Semantic retrieval
- Hybrid ranking
- Grounded answer generation
- Verifiable citations
- Missing-evidence handling

Investigate embedding options compatible with the existing configuration.

The current `.env` provides an OpenRouter API key and chat model name, but no dedicated embedding model.

Do not assume the configured chat model supports embeddings.

Recommend a feasible embedding approach, such as a suitable local embedding model, and document its resource requirements.

If semantic retrieval cannot be implemented with the available environment, identify that limitation explicitly rather than labeling keyword search as semantic RAG.

## 7. Define failure behavior

The assistant must handle:

- Missing API key
- Invalid model configuration
- OpenRouter outages
- Timeouts
- Rate limits
- Malformed tool calls
- Ambiguous employee names
- Missing inventory records
- Unauthorized documents
- Insufficient document evidence
- Prompt injection in retrieved documents

Retain the existing deterministic assistant as a fallback where possible.

Clearly distinguish fallback responses from LLM-generated responses.
