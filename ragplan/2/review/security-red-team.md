# Security red-team review and executable requirements

Date: 2026-11-16. This is an architecture attack analysis, not a penetration-test report. No malicious document was executed and no enterprise service exists to exploit. Existing safeguards are credited. **RBAC in the current demo is not production security.** Findings HR03 and HR05 describe credible failure schedules; the remaining tests below verify proposed boundaries and do not allege that every listed attack is currently possible.

Security violations block the corresponding confidential exposure regardless of retrieval accuracy. All test inputs, identity records, canaries, documents and browser traces must be synthetic. Never use imported workbook values as canaries. External enterprise inference remains prohibited, including supposedly public or sanitized data and hosted evaluation.

## Trust boundaries

| Boundary | Components and authority |
| --- | --- |
| B1 Browser → API | OIDC/session verification, request shape, CSRF/Origin, purpose and quotas. Browser headers/roles/tenant IDs are not authority. |
| B2 API → SQL | Trusted transaction-local context; runtime role subject to RLS; policy helpers with narrow privilege. API compromise remains inside the trusted computing base. |
| B3 Quarantine → parser | Hostile bytes enter a credential-free, no-network sandbox; a clean antivirus result does not confer trust. |
| B4 Parser → broker | Paths, schema, hashes, output cardinalities and source ownership are untrusted. A parser must not select another tenant's source or publish anything. |
| B5 SQL/evidence → models/UI | Only current authorized evidence, safe rendering and backend-issued references. Source text is data. |
| B6 Workers → lifecycle | Lease fence, exact predecessor manifest, tombstone and expected publication state govern adoption. Immutable blobs do not grant publication authority. |
| B7 Policy/journal → transport | Last authorization and deletion deny state must govern actual dispatch under the chosen failure model. This is HR03/HR05's unresolved boundary. |
| B8 Online stores → backup/restore/operators | Privileged custody, current revocation/delete/key watermarks, retention roots and sealed recovery. SQL snapshots alone are not current policy. |

## Dispatch guarantee counterexample

The smallest unexcluded schedule is:

1. A holds shared DB barrier, validates evidence, buffers payload, then pauses before handoff.
2. A's DB backend terminates; the DB releases its advisory lock while A's HTTP task remains alive.
3. B obtains exclusive barrier, revokes access, commits and acknowledges.
4. A resumes before it observes the lost session and hands the payload to transport.

The 250 ms timeout limits duration but does not remove the ordering violation. Repeating the check leaves a possible failure between the last check and send. HR03 is a protocol gap, not a request to recall already dispatched network bytes. The source proposal already correctly disclaims recall.

For a deliberately single-process pilot, a possible correction is to serialize **all** policy mutations and dispatch in one content-egress authority, with a singleton process lifetime, no bypass writers, and fail-closed restart reconciliation. This adds a constraint missing from the present multi-component protocol and needs failure tests. Multi-replica/HA operation requires an explicitly fenced dispatch protocol; adding more ASGI workers to the existing DB-lock design is not sufficient evidence. A bounded lease is an alternative only after its changed revocation semantics are approved.

## Test execution and release criteria

The review ran only finite synthetic models and the existing 46-test RAG suite as described in [the master report](hostile-review.md#verification-actually-performed). No ST security integration case above is marked passed. The [evidence model](evidence-check.py) can enumerate the lock-loss schedule; it does not simulate real ASGI/network/driver cancellation.

Required release evidence: actual SQL roles/connection pool; actual sandbox and egress policy; all API routes and both ordinary/staged resolvers; instrumented policy/transport races; source-to-derived purge inventory; sealed recovery against real test storage/journal; content-free logs; synthetic Playwright journeys using the actual enterprise API. Mocks may isolate model boundaries but cannot replace the policy, DB, journal or sandbox.

All tests must record expected authorization, command/configuration, actual result, safe trace/artifact and failure schedule. Run forbidden-result assertions on snippets, titles, aliases, facts, counts, scores, citation locators and model inputs. Require zero unauthorized disclosures or stale publications in the finite acceptance suite; do not describe that as proof of zero future security failures.
