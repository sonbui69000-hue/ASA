# Re-review of the reconciled RAG architecture

Date: 2026-11-16. Reviewed contract: **2.1.0**. Comparison baseline: [original HR01–HR14](hostile-review.md), [required changes](required-changes.md), and the other original review reports.

**The corrections repair most of the original architectural causes. They do not yet support an unconditional freeze of the complete schema, API and lifecycle protocol.** The remaining defects are concentrated in published semantic review, contract-family membership completeness, journal record identity and GC contract integration. They require targeted corrections, not a replacement of Python/PostgreSQL/private storage/local extraction or the evidence graph.

These verdicts distinguish a permanent architecture commitment from permission to learn through implementation. They do not require HA, a new vector database, a larger model, or final OCR/load measurements before synthetic engineering begins.

The decision packet explicitly records no approvals, so none of these findings is labelled ACCEPTED RISK. ## Required corrections

### RR01 — Published semantic retraction has no valid review subject

**High; confirmed contract incompatibility; HR06.** C08 line 176 requires a C11 package for the quality/classification/link/fact-retraction decision union. C11 line 446 restricts inspection to `awaiting_review/staged/accepted-but-unpublished`, and line 454 rechecks the package/assignment/scan/source at submission. C14 lines 498–504 and W15 require retraction or correction after publication without changing the source release. P05/P07 schedule the event/projection work but do not provide a second authorized review-subject path.

Witness: publish extraction E/release R with accepted amount F125; later discover a wrong installment. A reviewer requests a current package for E and is outside the staged predicate. A retained old package does not help: current subject/state is rechecked and packages expire. Reprocessing to create a staged extraction is not the promised immediate semantic retraction and can leave the original trust active until that workaround completes. This is an API/lifecycle defect visible without running a server, not evidence of a deployed leak.

Required correction before review API/schema freeze:

1. Define a strict review-subject union or a separate published semantic/policy decision route. Preserve the existing staged branch. The published branch must bind exact document/version/extraction/release and immutable fact/link/decision IDs, current review/retract capability, applicable source-read authority and expected semantic/decision revision. It must not depend on a currently staged package.
2. Define the published branch's safe evidence access and relevant classification/relation actions explicitly. A published correction capability must not become an unrestricted staged-reader or original-export capability. Semantic retraction must be possible without replacing canonical bytes; extraction corrections may still create a new extraction.
3. Apply the same S05 gate, C14 events, acceptance/projection/dependency invalidation, durable authority checkpoint, audit and current-response checks. Extend C08/C11/C14, S03/S05 and P05/P07 consistently rather than bypassing one predicate in implementation.
4. Amend T06 to start from a fully published subject, call the authorized API, test a denied peer and stale expected epoch, and retract/undo during a buffered answer with unchanged R/vector. Verify old trusted exact/alias filters disappear and old supported output is discarded.

Also align algorithm matrix **C07** (line 50), which still says **Implement Now** for a title/headings/**approved entity-ID** sketch, with C14 line 502's literal-only baseline and disabled semantic-derived sketches. State that baseline sketches contain literal source spans only. Normalized or linked semantic aliases belong in the live epoch-checked exact channel, or in a separately enabled projection with the specified invalidation/completeness contract. A dependency manifest alone does not make a retracted semantic value literal. C14 already provides the safe rule; the conflicting consumer description must adopt it.

Cost is small before route/projection implementation; later it requires changing review subjects, client workflows and potentially rebuilding semantic-bearing sketches. The existing epoch architecture can be retained.

### RR02 — Applicability does not bind the complete known family membership

**High; missing lifecycle/completeness invariant; HR02.** C12 line 462 gives a family a revision/current pointer. Lines 464–466 define a set's members and coverage of the original scope inventory. Line 472 validates submitted members and invalidates dependent sets on source replacement/retraction/deletion; line 474 explicitly handles membership/source deletion. Neither defines what **adding** a known family member does to an already-current set, nor requires the submitted manifest to account for all registered current family instruments. C13's response snapshot records family/set ID, without an explicit membership-head binding. C14's generic “invalidate affected” does not define how a set with no edge to the new member becomes affected.

Countermodel permitted by that omission: accepted S1 uses original O and amendment M1 and states payment 150. M2 is subsequently published and its family relationship is reviewed/registered, but its payment effect is still unknown. S1's existing releases and dependencies remain unchanged. A new request pins the latest semantic epoch and still selects S1; the epoch comparison alone does not prove S1 accounts for M2. Whole-selected-set authorization checks O/M1, not the omitted M2. This can produce a falsely complete current-obligation answer or ignore an inaccessible known amendment. It is a missing required invariant, not proof that an implementation has chosen this behavior.

Required correction before family schema/API freeze:

1. Define the family membership revision/head and its mutation rules. The existing family revision may serve this purpose if its meaning is explicit; a separate subsystem is unnecessary. Bind applicability approval to the exact membership head and source releases it considered.
2. Validate complete coverage of **registered family membership**, as well as original clause scopes. Each known current instrument must be accounted for as applicable, supplemental, explicitly excluded with reviewed reason/evidence, or pending/unknown/conflicting. Future-effective instruments remain accounted for even before their effects apply. This does not require discovery of documents never supplied to the service.
3. Addition or change of a reviewed membership/relation must atomically advance that head and invalidate the old current set, install an unknown/conflicting set, or install a complete reviewed replacement under the same gated transaction. Do not let an old accepted set silently survive a changed membership universe. An alternative is to allow membership edits only through a complete atomic applicability command; that command must validate against server-known membership.
4. Final legal-claim validation must verify the selected current set's membership binding. Apply conjunction authorization to the complete set and its decision evidence; unavailable required members yield the existing generic insufficient outcome. Independent permitted quotations may remain available without a claim of complete current applicability.
5. Extend T02 with M2 added **after** S1: pending effect, conflicting effect, future date, reviewed exclusion, and a caller denied M2. Include a request after the membership transaction, so a fresh semantic epoch cannot mask stale applicability.

This is the most expensive remaining semantic decision to postpone: incomplete accepted sets and their citations would need re-review after persistence. It does not reopen the corrected independent-instrument model or require automatic legal precedence.

### RR03 — Journal operation identity must support intent and commit records

**Medium; durable-format/idempotency ambiguity; HR05.** C16 line 524 says a unique operation ID makes journal entries idempotent. Line 528 adds a strict tagged union of `deny_intent` and `authority_commit`, both associated with an operation. S05 lines 73–79 requires intent, SQL commit and then authority checkpoint for a delete. W17 requires retrying operation X after an intent survived SQL rollback. The record identity/idempotency scope for the two entries is not specified.

If “unique operation ID” is implemented as global record uniqueness, X's commit record conflicts with X's earlier intent or is mistaken for its replay. Generating unrelated new operation IDs avoids that collision but leaves the correlation and command-retry semantics unspecified. A command ID can correctly own multiple records; the documents must say so. This is **not** a finding that the live deny topology still leaks, or that a unique constraint already exists in code. The foreseeable failure is a stuck/sealed operation or an incorrectly reconstructed checkpoint if consumers choose incompatible interpretations.

Required correction before ledger serialization/adoption:

1. Specify immutable per-record sequence/identity separately from command identity. Use a type-qualified idempotency key such as `(entry_kind, operation_id)`, or explicitly linked unique record IDs with a common parent operation ID.
2. Define same-kind/same-command/same-payload replay as the same durable record; changed payload is a conflict. State how an intent-only operation advances after confirmed SQL reconciliation, and how SQL-committed/checkpoint-missing recovery creates the checkpoint without repeating the mutation. Never erase an intent to resume access.
3. Include a short operation state/crash table for before intent, intent durable/SQL failed, SQL committed/checkpoint uncertain, checkpoint durable/Ack lost, and sealed restart. Preserve C16's independent anchor and behind-checkpoint fresh-approval rule.
4. Extend T05 to assert that one delete command produces both record types, including intent-only retry, commit-ack loss and a conflicting same-ID payload. The current finite deny-set check does not test this format.

This is inexpensive before serialization but costly once durable journals and recovery tools must read an incompatible format. It does not justify adding another database or event platform.

### RR04 — Root-aware GC does not yet fit the closed state/role contracts

**Medium; confirmed schema/privilege inconsistency; HR10.** C16 line 536 requires `gc_pending → purging → purged` and prevents new roots after claim. C06 line 91 lists artifact state as `staged/verified/adopted/purged`; line 131 requires exact state vocabularies. C06 line 135 restricts `rag_purger` to tombstoned targets. P07/migration0007 names the new GC fences but does not reconcile those closed contracts.

Example: a live document has active R2 and an expired, unrooted superseded R1 artifact. Retention GC should be able to claim R1 without tombstoning the live document. A literal tombstone-only purger cannot perform that cleanup. Broadening it ad hoc would remove the intended privilege boundary. Separately, an artifact cannot enter the prescribed intermediate states using only the listed enum.

Required correction before artifact/GC migration and role freeze:

1. Define pending/purging in an extended artifact enum or a separate explicit GC lifecycle/permit relation. If separate, specify how source validity, GC availability, CAS and “no new roots” predicates join it; do not overload immutable extraction quality state.
2. Authorize physical deletion only for a narrowly scoped authority-issued claim: confirmed tombstone deletion **or** expired/unreachable/unheld retention-GC target with exact artifact/storage-version identity and claim revision. Preserve roots/hold checks and serialize claim adoption under the same lifecycle lock.
3. Align C06, C16, role grants and migrations0002/0007. T10 must cover a rooted old artifact retained past TTL, unrooted superseded artifact of a live document, root creation before/after GC claim, hold races and idempotent physical deletion.

The retention-root mechanism itself is sound. This correction completes its state and capability expression; it is not evidence that the proposed sweep has already destroyed data.

### RR05 — Two bounded wording conflicts

**Low; align before their consumers freeze.** These do not restore the original HR03/HR04 causes.

- **Prewarm order:** C13 line 490 places prewarming inside the briefly gated cutover while also prohibiting a long encoder load there. W14 line 173 correctly prewarms before taking the gate. Specify load/prewarm and memory reservation outside the gate, then gated completeness/head revalidation and CAS. Do not hold the mutation gate through model loading.
- **Expiry claim:** W16 line 187 says expired rights “at enqueue” deny without the S05 line 59 suspension caveat. Match S05/I06/A09: expiry is evaluated at final gated admission with the conservative clock reserve; arbitrary OS suspension after that decision has no hard real-time lateness bound. Revocation Ack remains serialized behind the gate. If owners reject decision-time expiry, a separately enforceable deadline design is required; silently advertising zero lateness is not an alternative.

## Rechecked high-risk schedules

**Permission revocation during SQL failure:** In the selected model, killing the validating SQL backend cannot let another supported process acknowledge a revoke while the old process retains an unsent payload. The local gate remains held; a second process fails startup; a local mutation waits. Unknown SQL/mutation/send state seals rather than issuing a successful Ack. Confirmed predecessor death prevents a paused old sender resuming after takeover. This closes the original event schedule at design level. It depends on instrumenting the actual synchronous enqueue and excluding independent policy writers, not on a normal ASGI response wrapper. T03 is still necessary to establish that the implementation respects those premises.

**Deletion with durable intent but failed SQL:** The live authority installs the deny before permitting further egress, the SQL overlay excludes it before text/fact selection, resolver/model-input/final checks repeat current dependency denies, and 503 reports a durable deny rather than successful tombstoning. Purge waits for confirmed SQL tombstone. Missing/unknown journal state seals all content; the unsupported second-reader case is explicitly rejected. This is a substantive correction. RR03 concerns the remaining durable command lifecycle, not a requirement to tolerate unsupported replicas.

**Restore predating local revocation or semantic retraction:** Independent `authority_commit` checkpoints include authority revisions/head hashes; a delete-only journal is no longer presented as sufficient. SQL behind an acknowledged checkpoint remains sealed, invalidates restored grants/sessions/reviewer assignments/semantic/applicability/serving heads, and requires fresh approvals/rebuild. That prevents trusting an old accepted fact or grant merely because it survived in a backup. A09/A05 must accept the recovery availability cost and independent anchor/backup practice. Actual rollback/corruption and fresh-approval recovery remain T05/P09 tests; hash chaining alone is correctly not claimed to detect complete-file rollback.

**Embedding migration:** Eligible published sources cannot be omitted to make B appear complete. Publications maintain A and enqueue B delta; cutover validates both sides of membership against the latest source head. Old-profile responses are discarded after switch. Rollback uses current eligibility, not a restored old membership list. These are coherent safeguards. Optional dual-encoder online support depends on actual memory fit; a complete lexical maintenance path avoids making that an architectural prerequisite.

**Semantic updates and amendments:** The final epoch/current-acceptance guard correctly rejects an answer buffered before a retraction. It cannot compensate for an unreachable retraction API (RR01), or infer that an accepted applicability set includes a newly known family member (RR02). Those are pre-runtime contract gaps. No amount of vector-quality benchmarking closes them.

## Costly commitments and remaining gates

The corrected separation of source release, legal applicability, semantic trust and corpus representation should be preserved. The remaining corrections fit those boundaries. There is no substantiated reason here to flatten canonical evidence, collapse amendments into versions, add a remote LLM, or replace the retrieval stack.

Two proposed choices need explicit owner decisions because changing them later is expensive: **one host/one egress writer with custom synchronous transport integration**, and **sealed fresh-approval recovery rather than full policy/semantic operation replay**. They trade availability and recovery effort for a smaller correctness protocol. They are defensible for a bounded pilot, but an eventual requirement for HA or fast automatic recovery would reopen that design. The decision packet states this rather than concealing a future rewrite. A small transport/process-fencing spike should precede commitment to a particular ASGI/server adapter; this is not a request for production load certification first.

Required sequence:

1. Close RR01/RR02 in the proposed review/family contracts; settle RR03/RR04 durable state and privileges; align RR05. Obtain A01/A02a/A03/A09 for the dependent permanent boundaries. P00 should materialize strict tagged requests/responses, enums, ownership constraints and negative transition cases from that corrected design.
2. Build the isolated synthetic P03 lexical vertical slice with the pulled-forward minimal review, semantic/profile heads, journal deny, publication and final dispatch guards. Do not postpone those guards until a later “hardening” phase. Optional neural models need not block this slice.
3. Execute T01–T10 alongside their actual SQL/API/transport/storage consumers. In particular, test the published API route, new family membership, intent-plus-checkpoint lifecycle and retention GC privileges identified above. Before confidential intake, require actual-role/pool isolation, sandbox/no-egress, transport/process-fencing, durable-journal/delete and sealed-recovery evidence, plus real identity/data authority.
4. Use T11/T12/T14 and the E-series to qualify the chosen formats, automatic long-document scope, advertised scale, task quality and staffed review operations. Ratify A10/A11 at their acceptance gates. Include failures, stale responses, review time and abstentions. Larger-scale or optional-model results are required only when those capabilities are promoted. Run the planned Vitest/component and Playwright end-to-end workflows when the corresponding implementation/UI exists.

These are consumer-specific gates. Missing production measurements are not counted as additional design defects, and a synthetic success cannot establish confidential production safety.
